### [2026-08-24] | FEAT + DOCS | Push notification on/off preference, and documenting the previously-undocumented push pipeline

**What changed:**
Product wanted an explicit way to know whether a user has push notifications
enabled before sending one — previously nothing checked this. Investigation
found the push-sending pipeline was already partially live in production
but completely undocumented in this repo: a `push_notification` trigger
(`AFTER INSERT` on `notifications`) calling a `push` Edge Function via
`http_request`, plus an existing `device_tokens` table and
`register_device_token` SP. That Edge Function sent to every registered
token unconditionally, with no opt-out.

**Added:**
- `users.is_push_enabled boolean DEFAULT true` — account-level push preference
- `update_push_preference` SP — toggles the flag
- `get_user_v2` SP — same as `get_user`, adds `is_push_enabled` to the response (v1 kept, unchanged, per repo versioning convention)
- `device_tokens.is_active` — soft-delete flag for stale/reassigned tokens, consistent with `users.is_deleted` / `follows.is_active` elsewhere in this schema
- `push` Edge Function updated: checks `is_push_enabled` before sending; filters tokens on `is_active = true`; deactivates (not hard-deletes) tokens FCM reports as dead
- `register_device_token` updated (signature unchanged — `p_token`, not `p_fcm_token`, to avoid breaking existing callers): now verifies the user exists, and soft-deletes a token under any other user when it's re-registered to a new one (device switching accounts)
