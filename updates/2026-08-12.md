### [2026-08-12] | FIX (SP) | update_event_v2_4 threw "duplicate key value violates unique constraint uq_event_collaborators_active" on collaborator sync — DEPLOYED VERSION AFFECTED, REDEPLOY REQUIRED

**What happened (reported via actual request/response, against the already-redeployed corrected v2_4):** Calling `update_event_v2_4` with `p_scope: "all"`, `p_recurring_days: []`, and `p_collaborator_ids: ["1f513c0b-..."]` (a profile already an active collaborator on the event) returned:
```json
{"status": false, "message": "Something went wrong", "error": "duplicate key value violates unique constraint \"uq_event_collaborators_active\""}
```

**Root cause:** the invite/re-invite loop's "find existing row" lookup had no `ORDER BY`:
```sql
SELECT id, is_deleted INTO v_existing_collab_id, v_existing_deleted
FROM event_collaborators
WHERE event_id = v_collab_target_id AND profile_id = v_collab_id
LIMIT 1;
```
`event_collaborators` explicitly allows a profile to have **both** an old soft-deleted row and a current active row for the same `(event_id, profile_id)` at once — that's the mechanism that makes re-inviting after removal work at all. With no `ORDER BY`, this query can return either row nondeterministically. This event/profile pair had been added and removed enough times during testing that both a soft-deleted row and an active row existed simultaneously. When the query happened to return the soft-deleted one, the code's "already active → skip" check (`v_existing_deleted = false`) failed to match, so it fell through to the re-invite branch and tried to flip that soft-deleted row back to active — while the *other*, genuinely active row for the same profile still existed. Two active rows for the same `(event_id, profile_id)` violates `uq_event_collaborators_active`.

This bug has existed since **v2.0** — every version inherited it unchanged. It was latent until enough repeated add/remove/re-add testing on the same event+profile pair produced both row states at once (which is exactly the kind of testing this thread has been doing).

**Fix:** added `ORDER BY is_deleted ASC` to the lookup, so the active row (`is_deleted = false`) is always picked when one exists, instead of an arbitrary one.

**⚠️ This bug is present in the version of `update_event_v2_4` currently deployed to Supabase** (confirmed already redeployed once today with the earlier platform/collaborator-ordering fix, but before this one). **Requires another redeploy** of the SQL in `functions/events/update_event.md` (`V2.4 Function (Current)` block) + `NOTIFY pgrst, 'reload schema';` to take effect.

### [2026-08-12] | FIX (SP) | update_event_v2_4's un-recur path wiped platforms/collaborators sent in the same request (bug introduced by an earlier fix today)

**What happened (reported via actual request/response before → update → after):** Called `update_event_v2_4` on a recurring child occurrence with `p_recurring_days: []` (remove recurring) plus `p_platforms: [{platform_id:1, stream_url:...}]` and `p_collaborator_ids: [2 existing profile ids]` in the same request. Result: `parent_event_id`/`is_recurring`/`recurring` correctly cleared, but `platforms` came back `[]` (should have been the YouTube platform sent) and both collaborators came back with a refreshed `invited_at` (should have stayed untouched — they were already active).

**Root cause:** The un-recur collapse block (added earlier today) ran *after* Branch A/B in execution order. Branch A/B writes `p_platforms`/scalar fields to `v_target_parent_id`, which at that point was still the **old hidden template** (`997824c5`) — the collapse hadn't repointed it to `p_event_id` yet. So the new platform got inserted onto the template, and then the collapse block deleted that template a few statements later, cascading the just-written platform away with it. Same story for collaborators: they lived on the template under its `event_id`; the template got deleted; the sync step (which by then *did* correctly target `p_event_id`) found no existing rows there and treated both profiles as brand-new invites.

**Fix:**
1. Moved the entire un-recur collapse block to run **before** Branch A/B (right after collaborator-target resolution, before the `'this'`/`'all'` scope branches) — so by the time Branch A/B writes platforms/scalars/collaborator-sync targets, `v_target_parent_id`/`v_collab_target_id` already point at the surviving `p_event_id`, not a row about to be deleted.
2. Added a copy step: before deleting the old template, its existing `event_platforms`/`event_collaborators` rows are copied onto `p_event_id` (only if `p_event_id` doesn't already have its own) — so a bare "just remove recurring" call, with no `p_platforms`/`p_collaborator_ids` in the same request, doesn't strip data `p_event_id` was only seeing via `COALESCE(parent_event_id, event_id)` fallback.

Manually traced the reported request against the corrected logic: platforms now end up as `[youtube]` (matches what was sent), and both collaborators are recognized as already-active with their original `invited_at` preserved.

**Version note:** still folded into `update_event_v2_4` in place — not yet deployed, no live callers to break.

### [2026-08-12] | FIX (SP) | update_event silently deleted the edited occurrence's own platforms/collaborators when editing an established recurring series' rule

**What happened (reported via screenshot):** Profile page showed one recurring occurrence ("test123") with "No Info — No links or collaborators available" while a sibling occurrence ("teat") still showed its platform icons (Twitch, Kick). General complaint: "All data regarding collaboration and links are removed automatically when updated."

**Root cause (full audit of `update_event_v2_4`, start to end, as requested):**
In the "recurring rule + regen" block, editing the recurring rule of an **already-established** series (`p_scope='all'` + non-empty `p_recurring_days`, NOT a first-time conversion) ran:
```sql
IF v_is_first_conversion THEN
    DELETE FROM event_mst WHERE parent_event_id = v_target_parent_id AND event_id != p_event_id;
ELSE
    DELETE FROM event_mst WHERE parent_event_id = v_target_parent_id;   -- deletes EVERY child, no exception
END IF;
```
This has existed since **v2.2** and was explicitly left "unchanged from v2.2" through v2.3 — a deliberate scope decision at the time, but the actual bug. If `p_event_id` (the occurrence the caller is editing) is itself a **child** occurrence rather than the hidden template, this deletes it along with every sibling. `event_platforms`/`event_collaborators` cascade-delete with it (`ON DELETE CASCADE`). A brand-new row with a **different `event_id`** is generated for that same date, but new occurrences are only ever seeded with the series template's platforms/collaborators via read-time `COALESCE(parent_event_id, event_id)` fallback — never with whatever was individually overridden (`is_overridden`/`collaborators_overridden = true`) on the row that just got deleted. That override is gone permanently. This fires on **every** `update_event` call that includes a non-empty `p_recurring_days` with `p_scope='all'` against an established series — which, per the earlier recurring-days fix, is very likely sent on every single edit if the client always resends the event's current recurring days rather than omitting the field. That matches "removed automatically when updated" exactly.

**Fix:** `p_event_id` is now **always** excluded from the delete-and-regenerate step, not just on first conversion:
```sql
DELETE FROM event_mst WHERE parent_event_id = v_target_parent_id AND event_id != p_event_id;
```
The occurrence actually being edited keeps its own `event_id`, and therefore its own `event_platforms`/`event_collaborators` rows, across any recurring-rule edit. Every other sibling occurrence is still deleted and regenerated fresh, same as before — this only protects the one row the caller is actively editing.

**Version note:** folded into `update_event_v2_4` in place (not yet deployed — see prior entries below), same reasoning as the earlier in-place edits today: no live callers exist yet to break.

### [2026-08-12] | FIX (SP) | update_event had no code path to convert a recurring event back to non-recurring

**What happened (reported via Flutter request/response):**
Editing a recurring event and sending `p_recurring_days: null` (along with the other `p_recurring_*` fields all `null`) to try to clear its recurrence returned `status: true` / "Event updated successfully", but the event was still recurring afterward — nothing about `is_recurring`, `event_recurring`, or the sibling occurrences changed.

**Root cause:**
Every version of `update_event` up to and including `v2_3` only ever acted on the recurring rule when `v_update_recurring` was true, which required `p_recurring_days IS NOT NULL AND array_length(...) > 0`. Passing `null` — or even `[]` — both fell through as "no rule change" per the function's own documented contract. There was **no code path anywhere in the function that could set `is_recurring = false`**, delete `event_recurring`, or remove sibling occurrences. A recurring event could never be un-recurred through this API, regardless of what was sent.

**Fix — `update_event_v2_4`:**
- `p_recurring_days: []` (empty array, **not** `null`) is now the explicit "make this event non-recurring" signal — matching the null-vs-`[]` convention already used by `p_platforms` (`null` = don't touch, `[]` = clear) and `p_collaborator_ids` in this same function. `null` still means "leave recurrence untouched" — unchanged.
- Only valid with `p_scope='all'` — `p_scope='this'` + `p_recurring_days=[]` is rejected with the same "use scope 'all'" error already used for adding/changing a rule.
- No-op if the event isn't currently part of a recurring series.
- On removal: deletes every sibling occurrence and the `event_recurring` rule row, then collapses `p_event_id` back into a standalone event — if it was a child occurrence, it absorbs the series identity (`parent_event_id = NULL`, `is_recurring = false`) and the now-orphaned hidden template row is deleted (the v2.3 first-conversion logic, run in reverse); if `p_event_id` was itself the hidden template/parent, `is_recurring` is simply flipped to `false` on it directly.

**Function changed — new version, per this repo's naming convention:**

| Function | Old (still live) | New (current) | Change |
|---|---|---|---|
| `update_event` | `update_event_v2_3` | **`update_event_v2_4`** | Adds the missing "convert recurring → non-recurring" path via `p_recurring_days: []`. No other param changes. |

Old `update_event_v2_3` kept live and unchanged under "V2.3 Function (Previous)" in `functions/events/update_event.md` for existing callers.

**No schema migration required** — reuses existing columns/cascades (`parent_event_id ON DELETE CASCADE`, `event_recurring.event_id ON DELETE CASCADE`, etc.).

**Deployment:** brand-new function name (`update_event_v2_4`), not an overload replacement — nothing to drop. Deploy it, then:
```sql
NOTIFY pgrst, 'reload schema';
```
Then point the Flutter app at `/rpc/update_event_v2_4` instead of `/rpc/update_event_v2_3` — **and switch the "clear recurring" request payload from `p_recurring_days: null` to `p_recurring_days: []`**, since that's the new trigger for removal.

**Status:** Doc change complete in `functions/events/update_event.md`. Not yet deployed to the live Supabase database — pending deployment + retest:

2. Repeat targeting the hidden template row directly (if reachable) → confirm it also flips to non-recurring in place, no orphaned children left behind.

4. Re-run the v2.3 first-conversion and v2.2 collaborator-scope regressions to confirm no impact from the new code path.
