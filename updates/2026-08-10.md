### [2026-08-10] | FIX (SP) | update_event_v2_1 'this' scope changed p_is_collaborative for the whole recurring series

**What happened:**
Follow-up to the 2026-08-06 collaborator-scoping fix (see `updates/2026-08-06.md`). After deploying `update_event_v2_1`, per-occurrence collaborator changes worked correctly, but a related field did not: calling `update_event_v2_1` with `p_scope='this'` and `p_is_collaborative=false` (e.g. when the Flutter app clears the last collaborator from a single occurrence and derives `is_collaborative: false` for that occurrence) turned off `is_collaborative` for **every** occurrence in the recurring series, not just the one being edited.

**Confirmed via actual Flutter request/response:**
```
p_event_id: 17c737ed-...  (single occurrence)
p_scope: this
p_collaborator_ids: []
p_is_collaborative: false
```
This call succeeded (`status: true`) but the "SHARED: is_collaborative" block unconditionally wrote to the parent + all children.

**Root cause:**
Unlike collaborators (which needed the new `collaborators_overridden` flag + per-occurrence rows), `is_collaborative` was already stored directly on every `event_mst` row, and every read function (`get_event_by_id_v2`, `get_profile_events_v2_1`, `get_event_list_v2`) already reads `e.is_collaborative` from each row directly with no parent fallback. The bug was purely in the write path: the "SHARED: is_collaborative" block in `update_event_v2_1` ignored `p_scope` entirely and always wrote to `v_target_parent_id OR parent_event_id = v_target_parent_id` (documented as intentional "always parent-level" in v2.0/v2.1, but never revisited once per-occurrence collaborators were introduced on 2026-08-06).

**Fix — made the same block scope-aware, no schema change needed:**
- `scope='this'` → `UPDATE event_mst SET is_collaborative = p_is_collaborative WHERE event_id = p_event_id` (only the occurrence).
- `scope='all'` → unchanged, still updates parent + all children.
- Also fixed the `v_effective_is_collab` lookup (used by the collaborator-limit-reject check) to read from `v_collab_target_id` (the occurrence for `scope='this'`, the parent for `scope='all'`) instead of always the parent, so the "cannot add collaborators when is_collaborative is false" check reflects the correct row.

**Function changed — new version, per this repo's naming convention:**

| Function | Old (still live) | New (current) | Change |
|---|---|---|---|
| `update_event` | `update_event_v2_1` | **`update_event_v2_2`** | `p_is_collaborative` write scoped to `p_event_id` when `scope='this'`; `v_effective_is_collab` lookup fixed to match. No param changes. |

Old `update_event_v2_1` kept live and unchanged under "V2.1 Function (Previous)" in `functions/events/update_event.md` for existing callers.

**No schema migration required** — `is_collaborative` already exists per-row; no new column, no read-path changes.

**Deployment:** brand-new function name (`update_event_v2_2`), not an overload replacement — nothing to drop. Deploy it, then:
```sql
NOTIFY pgrst, 'reload schema';
```
Then point the Flutter app at `/rpc/update_event_v2_2` instead of `/rpc/update_event_v2_1`.

**Status:** Doc change complete in `functions/events/update_event.md`. Not yet deployed to the live Supabase database — pending deployment + retest (call `update_event_v2_2` with `p_scope='this'` and `p_is_collaborative=false` on one occurrence, confirm sibling occurrences keep their original `is_collaborative` value; then `p_scope='all'` and confirm it still propagates to the whole series as before).
