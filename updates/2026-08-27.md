### [2026-08-27] | FIX | `get_profiles_v2_1` runtime error: `missing FROM-clause entry for table "p"`

**What changed:**
Creator Search calls (via `get_profiles_v2_1`) were failing outright with
`{"status": false, "error": "missing FROM-clause entry for table \"p\""}` for
any keyword search. Root cause: the `platforms` and `additional_links`
subqueries built their `json_build_object` from `p.plat_id` / `p.logo_url`
(and, in `get_profile_by_id_v2_1`, `cpa.*` / `p.*` / `pcl.*`), but those
aliases only exist inside the `LATERAL` subquery that computes `sort_order` —
outside it, only the LATERAL's own alias (`platform_list` / `additional_list`
/ `custom_list`) is in the query's FROM list. This is invalid SQL, not a typo
that happened to still run — every call to the affected groups errored at
execution time.

Same out-of-scope-alias mistake was also present in my earlier same-day
`get_profiles_v2` ordering patch (see entry below) — caught and fixed before
that version was ever deployed — and in `get_profile_by_id_v2_1`, which
wasn't reported broken but has the identical pattern and would fail the same
way on redeploy.

**Fixed:**
- `get_profiles_v2_1` — `platforms`/`additional_links` outer `json_build_object`
  now reference `platform_list.*`/`additional_list.*` instead of `p.*`.
- `get_profiles_v2` — same fix applied (not yet deployed, so never actually
  broken in production, just corrected before it could be).
- `get_profile_by_id_v2_1` — `platforms`/`additional_links`/`custom_links` now
  reference `platform_list.*`/`additional_list.*`/`custom_list.*` instead of
  `cpa.*`/`p.*`/`pcl.*`. Preventive — not confirmed broken in production, but
  the doc's SQL had the identical defect.
- All three: same function/endpoint names, same response shape — redeploy
  only, no client change.

**Files:**
- [[functions/profiles/get_profiles.md]] — `get_profiles_v2_1` and `get_profiles_v2` SQL + version history
- [[functions/profiles/get_profile_by_id.md]] — `get_profile_by_id_v2_1` SQL + version history

**Still needed (not done in this session):**

  in Supabase and reload the PostgREST schema cache

### [2026-08-27] | FIX | `get_profiles_v2` platform icons now match profile-page order

**What changed:**
Creator Search showed platform icons in a different order than the creator's
own profile page for the same profile. Traced to `get_profiles_v2`'s
`platforms` subquery: it built the array with plain `json_agg` and no
`ORDER BY`, so rows came back in whatever order the
`creator_platform_accounts` ⋈ `platforms` join happened to produce — not the
user's saved drag-drop order. `get_profile_by_id_v2_1` was already sorting
correctly via `array_position` against
`profile_link_preferences.platform_ids_order`.

**Fixed:**
- `get_profiles_v2` — platforms subquery rewritten to the same `LATERAL` +
  `sort_order` pattern already used by `get_profile_by_id_v2_1` and by the
  current `get_profiles_v2_1`/`get_profiles` (v3): preference position when
  set, else `plat_id + 100` as a stable fallback. Response shape unchanged
  (`platform_id` + `logo_url` only) — no client change required, just
  redeploy the SQL and `NOTIFY pgrst, 'reload schema';`.

**Files:**
- [[functions/profiles/get_profiles.md]] — patched `get_profiles_v2` SQL + version history
- [[docs/api/profiles/get_profiles.md]] — version comparison table updated

**Still needed (not done in this session):**
- Redeploy `get_profiles_v2` in Supabase and reload the PostgREST schema cache
  for the fix to take effect in production.
