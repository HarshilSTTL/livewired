### [2026-08-11] | FIX (SP) | update_event_v2_2 duplicated the edited event and left `recurring` null when converting a non-recurring event to recurring

**What happened (reported by QC):**
Create a non-recurring event, then edit it to add `p_recurring_days`/`p_recurring_type`/etc. (scope demotes `'this'` → `'all'` since the event has no parent yet). The event does get converted to recurring, but:
1. The event being edited is **not** part of the resulting series — instead a brand-new duplicate instance is created for the same day/time.
2. Every generated occurrence (including the duplicate) reads back `"recurring": null` from `get_event_by_id_v2`, even though `"is_recurring": true`.

**Confirmed via actual Flutter request/response:**
```
p_event_id: ce599aff-...  (single, non-recurring event)
p_scope: this   → demoted to 'all' (no parent yet)
p_recurring_days: [Mon..Sun]
p_recurring_type: weekly
p_recurring_start_date: 2026-08-11
```
Read-back for the newly generated child (`8a02b4f1-...`, `parent_event_id: ce599aff-...`) showed `is_recurring: true` but `recurring: null`.

**Root cause (two bugs in the same code path):**
- **Duplicate:** `update_event_v2_2`'s regen block always treats `p_event_id` as the series' parent/template row (`parent_event_id IS NULL`) and regenerates *all* child occurrences from scratch, including one for the same date as `p_event_id` itself. `get_profile_events` excludes `(is_recurring = true AND parent_event_id IS NULL)` rows from listings — so the originally-edited event disappears from the calendar and the freshly generated row takes its place, looking like a duplicate.
- **`recurring: null`:** the regen block only ever ran `UPDATE event_recurring ... WHERE event_id = v_target_parent_id`. On a first-time conversion there is no existing `event_recurring` row for that id, so the `UPDATE` silently affects 0 rows — the series is generated with **zero** rows in `event_recurring`, and every read (`get_event_by_id_v2`'s `recurring` subquery, keyed on `COALESCE(parent_event_id, event_id)`) returns `null`.

**Fix — `update_event_v2_3`:**
- Detect first-time conversion (`parent_event_id IS NULL` and `is_recurring` was `false` before this call). On that path only:
  - Create a new hidden template row (`parent_event_id = NULL`, `is_recurring = true`) to own the recurrence rule.
  - Copy `p_event_id`'s platforms and already-active collaborators onto the new template (siblings fall back to `COALESCE(parent_event_id, event_id)` for both when not individually overridden).
  - Re-point `p_event_id` at the new template (`parent_event_id = <template>`, `is_recurring = true`) instead of leaving it as the hidden template — it stays visible as the series' first occurrence.
  - Skip generating a duplicate occurrence for the date `p_event_id` already occupies.
- `event_recurring` is now upserted (`UPDATE`, then `INSERT` if `NOT FOUND`) instead of only `UPDATE`d, for both first conversions and normal series edits.
- Editing an already-established recurring series is unchanged — the delete-all/regenerate-all behavior for that path is left exactly as in v2.2 to avoid any regression there.

**Function changed — new version, per this repo's naming convention:**

| Function | Old (still live) | New (current) | Change |
|---|---|---|---|
| `update_event` | `update_event_v2_2` | **`update_event_v2_3`** | First-time non-recurring→recurring conversion reuses `p_event_id` as the series' first occurrence instead of duplicating it; `event_recurring` upserted instead of only updated. No param changes. |

Old `update_event_v2_2` kept live and unchanged under "V2.2 Function (Previous)" in `functions/events/update_event.md` for existing callers.

**No schema migration required** — reuses existing columns (`parent_event_id`, `is_recurring`, `is_overridden`, `collaborators_overridden`) exactly as `create_event_v3` already does for brand-new recurring events.

**Deployment:** brand-new function name (`update_event_v2_3`), not an overload replacement — nothing to drop. Deploy it, then:
```sql
NOTIFY pgrst, 'reload schema';
```
Then point the Flutter app at `/rpc/update_event_v2_3` instead of `/rpc/update_event_v2_2`.
