### [2026-09-24] | FIX | `update_event_v2_6` reset already-accepted collaborators back to `pending`

**What changed:**
QC reported: on any event, accept a pending collaborator invite, then edit the
event to invite one more collaborator — the already-accepted collaborator's
status silently flips back to `pending` too, even though it was never
touched. Two separate bugs, found from an actual request log:

1. **`p_collaborator_ids` was a full sync/replace list, not an append list.**
   `null` = don't touch, `[]` = remove all, `[ids]` = keep only those ids and
   soft-delete anyone else. A caller that sent only the newly-invited id (not
   the full current roster) would soft-delete every other collaborator: if
   that already-accepted collaborator was later re-added, the function found
   their soft-deleted row and reset `status` back to `'pending'` on
   reactivation. Removal-by-omission added nothing `remove_collaborator`
   didn't already cover as its own dedicated endpoint.

2. **`p_scope='this'` reset an inherited collaborator when first creating a
   per-occurrence override**, even when the caller correctly sent the full
   list (confirmed from a real request log with `p_scope: "this"` and both
   the accepted + new collaborator ids). Collaborator rows for `scope='this'`
   are keyed to the occurrence's own `event_id`, separate from the series
   parent's rows. An occurrence that had never had its own override before
   had no row there for the already-accepted profile (their row lives on the
   parent), so the function treated them as brand new and inserted a fresh
   `status='pending'` row — while also flipping `collaborators_overridden =
   true`, switching that occurrence's reads away from the parent's (still
   `accepted`) row to its own new pending one.

**Fixed (same function/endpoint name, `update_event_v2_6` — in-place patch,
no client migration needed):**
- `p_collaborator_ids` is now append/reactivate-only. `null` and `[]` are
  both no-ops; a non-empty list only invites/reactivates the ids given and
  never removes anyone not in the list. Use `remove_collaborator` for
  removal.
- When `p_scope='this'` first creates an occurrence-level override for a
  profile that has no row yet at the occurrence but is already active
  (`pending`/`accepted`) at the series parent, that status is now copied
  down onto the new occurrence-level row instead of resetting to `pending`
  (same "copy from parent" pattern already used elsewhere in this function
  for recurring-series conversion).
