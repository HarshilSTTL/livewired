### [2026-08-20] | FEAT (SCHEMA + SP) | Explicit event_end_date — fixes end time being allowed before start time

**Client requirement:**
> End time for event can be before start time; this should not be possible. Event creator should include end date option as well as end time so that an event can safely run past midnight, and default end date should be same as start date.

**Root cause:**
`event_mst` only ever had one `event_date` shared by both start and end — `event_end_time` was a bare `time`, not a datetime. `create_event_v3` and `update_event_v2_4` both *intentionally* allowed `event_end_time < event_time`, treating it as an implicit "runs past midnight, ends the next day" signal, and only rejected exact time-of-day equality. That convention was ambiguous (no column actually recorded the end date — every read function re-derived it with `CASE WHEN event_end_time < event_time THEN event_date + 1 ELSE event_date END`) and inconsistent with `check_event_conflict_v2`, which did the opposite: it **rejected** `start_time >= end_time` outright and assumed the end time always fell on the same calendar day, so a cross-midnight event could never be conflict-checked correctly in the first place.

**Fix — added `event_mst.event_end_date` and made every function that reads or writes event times aware of it:**

| Function               | Old (still live)          | New (current)                 | Change                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------- | ------------------------- | ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `create_event`         | `create_event_v3`         | **`create_event_v4`**         | Adds `p_event_end_date` (defaults to `p_event_date`). Validation now compares the full `(date, time)` pair — `end_time < start_time` is only valid when an explicit later `event_end_date` makes the combined end datetime later. Recurring occurrences carry the day offset (end date minus start date) so a multi-day recurring event keeps its duration on every occurrence. |
| `update_event`         | `update_event_v2_4`       | **`update_event_v2_5`**       | Adds `p_event_end_date` (`null` = leave untouched, same convention as every other field). Same full-datetime validation for both `p_scope='this'` and `p_scope='all'`. Recurring rule regeneration reapplies the day offset to every freshly generated sibling.                                                                                                             |
| `check_event_conflict` | `check_event_conflict_v2` | **`check_event_conflict_v3`** | Adds `p_event_end_date`. Fixes the pre-existing bug where both the new event and every existing row assumed the end time fell on the same calendar day — cross-midnight events can now be checked (and are no longer rejected outright).                                                                                                                                    |
| `get_event_by_id`      | `get_event_by_id_v2`      | **`get_event_by_id_v3`**      | Adds `event_end_date` to the response; `event_end_time` now derives from the real column instead of inferring "next day".                                                                                                                                                                                                                                                   |
| `get_profile_events`   | `get_profile_events_v2_1` | **`get_profile_events_v2_2`** | Same change as above.                                                                                                                                                                                                                                                                                                                                                       |
| `get_event_list`       | `get_event_list_v2`       | **`get_event_list_v3`**       | Same change, applied identically across all 4 date branches (PAST / LIVE / TODAY / FUTURE) — including the LIVE-window "has started / has not yet ended" and "currently live, exclude from TODAY" checks, which previously used the same implicit next-day inference.                                                                                                       |

**Schema migration required:**
```sql
ALTER TABLE public.event_mst ADD COLUMN IF NOT EXISTS event_end_date date NULL;

-- Backfill existing rows so old cross-midnight events (under the pre-event_end_date
-- convention) get a correct end date instead of NULL:
UPDATE public.event_mst
SET event_end_date = CASE WHEN event_end_time IS NOT NULL AND event_end_time < event_time
                           THEN event_date + 1 ELSE event_date END
WHERE event_end_time IS NOT NULL AND event_end_date IS NULL;
```

**Deployment:** all 6 functions are brand-new function names — no overloads to drop. Run the migration above first, deploy the new functions, then:
```sql
NOTIFY pgrst, 'reload schema';
```
Point the client at `create_event_v4`, `update_event_v2_5`, `check_event_conflict_v3`, `get_event_by_id_v3`, `get_profile_events_v2_2`, and `get_event_list_v3`. Every old version is kept live and unchanged under its own "(Previous)" section in each doc for existing callers.

**Status:** Doc changes complete. Not yet deployed to the live Supabase database — pending migration + deployment + retest (create an event with `event_time=23:00`, `event_end_time=01:00`, no `p_event_end_date` → should succeed and read back `event_end_date` one day after `event_date`; same request with `p_event_end_date` equal to `p_event_date` should now be rejected).

**Note:** the actual event-creation UI (date/time pickers) lives outside this repository — this repo only contains the backend SQL function specs, schema docs, and a static marketing page. The UI will need a corresponding end-date field added wherever it currently only exposes start/end time.
